# SnapMoment – Project Assumptions

This document records the assumptions used while designing and implementing SnapMoment. These assumptions define the scope of the college/demo version and should be reviewed if the project is used for a real public event.

## 1. Visitor Identity

1. A visitor can create a profile by entering a name; an email address is not required.
2. Each new visitor receives a unique Visitor ID generated by the application.
3. On the same browser, a visitor is recognised using a long-lived, HTTP-only cookie containing a visitor token.
4. On another browser or device, a returning visitor can enter their name and Visitor ID to retrieve the existing profile.
5. Visitor IDs are assumed to be kept private by the visitor. A name and Visitor ID are not strong identity verification.

## 2. Photo Uploads

1. Visitors may upload JPG/JPEG, PNG, and WEBP images only.
2. A visitor may select up to 20 photos in one upload request.
3. Each image must be no larger than 8 MB.
4. The combined upload size must not exceed 40 MB.
5. The server validates the detected MIME type and checks that the file is a valid image; it does not rely only on the filename extension.
6. The server generates random filenames so that two uploads with the same original filename do not overwrite one another.
7. The original filename is retained as metadata; the generated filename is used for storage.
8. Uploaded photos are stored in the project's `uploads/photos` directory.

## 3. Consent, Privacy, and Moderation

1. Visitors are responsible for confirming that the selected photos are okay to share at the event by checking the consent box.
2. Consent in this demo is a simple checkbox confirmation; it is not a legal consent-management workflow.
3. Every uploaded photo starts with `pending` status.
4. An administrator must approve a photo before it appears in the public gallery or slideshow.
5. Rejected photos remain visible in the admin moderation area until permanently deleted.
6. Permanent deletion is available only for rejected photos in the admin interface.
7. When a rejected photo is deleted, the corresponding database row and image file are intended to be removed.
8. The project assumes the event organiser has the authority to moderate submitted photos and handle deletion requests.

## 4. Gallery and Slideshow

1. The public gallery contains approved photos from all visitors, not only the current visitor.
2. The public gallery is refreshed periodically so that newly approved photos can appear without a full page reload.
3. The display page rotates through approved photos every 6 seconds.
4. The display page checks for changes to the approved-photo list every 10 seconds.
5. If there are no approved photos, the display page shows an empty-state message.
6. The 3D-style carousel is a presentation feature; it does not change the photo approval rules or database records.

## 5. Administrator

1. The first admin account is created automatically when the admin table is empty.
2. The initial local demo credentials are `admin` / `admin123`.
3. The default credentials are not suitable for public deployment and must be replaced before the site is exposed to the internet.
4. Only authenticated administrators should access the moderation panel.

## 6. Technical Environment

1. The project is developed for PHP and MySQL using XAMPP on a local machine.
2. The supplied `config/db.php` uses MySQL port `3307`; another environment may require a different port.
3. The database name is `snapmoment_db`.
4. The project uses PHP PDO and MySQL InnoDB tables.
5. The upload directory must be writable by the PHP/Apache process.
6. PHP configuration must permit the documented upload sizes.

## 7. Scope and Constraints

1. This version is intended as a college project/local demonstration, not a fully hardened commercial event platform.
2. HTTPS, production secrets management, rate limiting, stronger visitor identity verification, automated backups, and production hosting configuration are outside the current local-demo setup.
3. Simultaneous uploads are expected not to overwrite each other's files because random filenames are generated; the behaviour must still be tested under the actual deployment environment.
4. The application does not assume that a visitor's name is unique. The Visitor ID distinguishes profiles.
5. The application does not automatically delete old approved or rejected photos based on age or storage limits.
